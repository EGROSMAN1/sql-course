The data is synthetic. The city and country names are real, but every student, course, instructor, program and number in the file were artificially generated with a fixed random seed. Nothing about a real educational institution should be inferred from them.

Before we start — building the model. Load the model's eight tables (Relationships it's a documentation sheet — don't load it). Turn off Autodetect, build the seven relationships manually, and make sure they're all One to Many in the direction Single from the dimension to Fact_Enrollments. Mark the Dim_Date as a date table (Mark as date table on Full_Date).

The big trap in this file — canceled rows that carry unrealized revenue. In the fact table there are two money columns that look like twins: Tuition_Billed_USD andTuition_Collected_USD. for every row whose status belongs toStatus_Group = "Lost" — meaning Withdrawn andCancelled — there's a positive charge but collection zero. Whoever sums the charge column will get 61,236,519.19 instead 50,294,056.87 — inflation of 10,942,462.32 dollars, 17.9% of the total billed, that never made it to the register. Throughout the whole assignment, we sum Tuition_Collected_USD. A charge is an intent, collection is revenue.

Matching brackets. Table[Column] = column · [measure] = square brackets without a table name. For each measure: right-click on Fact_Enrollments in the panel Data ← New measure ← the formula ← Enter. The name must be exactly as it appears in the exercise.

1.1 · Total Tuition Collected — the base measure

Create a measure named Total Tuition Collected that summarizes the Fact_Enrollments[Tuition_Collected_USD]. Format with a thousands separator and two decimal digits.

Total Tuition Collected =
SUM (
  Fact_Enrollments[Tuition_Collected_USD]
)
  1. creationRight-click on Fact_Enrollments ← New measure
  2. designMeasure tools ← Format: Currency ← 2 digits
  3. checkDrag onto an empty card to make sure the number appears

Why this specific column: In the table also sits Tuition_Billed_USD, and it returns 61,236,519.19. The difference of 10,942,462.32 The dollar is exactly the charge of the canceled rows — money that was recorded as a debt and was never collected. Exercise 4.1 breaks this down completely.

result: 50,294,056.87 dollars — the anchor number of the whole assignment.

1.2 · Students Enrolled — how many students, really

Create a measure named Students Enrolled That counts students unique based on Fact_Enrollments[Student_ID].

Students Enrolled =
DISTINCTCOUNT (
  Fact_Enrollments[Student_ID]
)

Why not COUNT: COUNT(Student_ID) would return 28,640 — it counts rows that have a value, not unique values. Each student enrolls in 6.8 courses on average, hence 28,640 ÷ 4,198 ≈ 6.82.

result: 4,198 Students.

1.3 · Tuition per Student — the Lego principle

Create a measure named Tuition per Student — strictly from the two existing measures, without the division sign / and without AVERAGE. Format to two decimal places.

Tuition per Student =
DIVIDE (
  [Total Tuition Collected],
  [Students Enrolled]
)

The average of what: AVERAGE(Tuition_Collected_USD) would return the average per enrollment record (1,756.08), not per student. When the measure is built from two existing measures, the denominator is explicitly defined and you know exactly what you divided. DIVIDE Preferable to / because it returns blank instead of an error when the denominator is zero.

The measure automatically rolls up to any context: Drag it onto the programs table and it will return the tuition per student for each program separately — without writing another line.

result: 11,980.48 Dollar per student.

1.4 · Total Credit Hours — SUM on a different column

Create a measure named Total Credit Hours that summarizes the Fact_Enrollments[Credit_Hours]. The measure serves the combo chart in exercise 2.10.

Total Credit Hours =

This column is truly derived: Credit_Hours in the fact table always equals Credit_Value of the course in-Dim_Course. You could have skipped it and aggregated through the relationship — it sits in the fact table so you can aggregate without touching the dimension.

1.5 · Courses Delivered — a second DISTINCTCOUNT

Note the difference from 1.2: The same function, a different column, and a result of an entirely different magnitude. 1.6 · Online Tuition — first CALCULATE

Create a measure named Online Tuition that returns the tuition collected from online courses only. Use CALCULATE with [Total Tuition Collected] As an expression and a condition on Dim_Course[Delivery_Mode].

Online Tuition =
CALCULATE (
  [Total Tuition Collected],
  Dim_Course[Delivery_Mode] = "Online"
)

What happens here: CALCULATE adds the condition to the filter context and only then runs the [Total Tuition Collected]. The filter sits on a text column in the dimension table, flows through the relationship to 28,640 fact rows — without any JOIN.

result: 14,331,147.98 dollars — 28.49% of total collection.
The full breakdown: Campus 24,521,003.34 · Online 14,331,147.98 · Hybrid 11,441,905.55

1.7 · Realized Tuition — CALCULATE with KEEPFILTERS

Create a measure named Realized Tuition that returns only the collection from records that ended — Dim_Status[Status_Group] = "Realized". Wrap the condition inKEEPFILTERS.

Realized Tuition =
CALCULATE (
  [Total Tuition Collected],
  KEEPFILTERS (
    Dim_Status[Status_Group] = "Realized"
  )
)

What KEEPFILTERS changes: A regular condition inside CALCULATE overrides Every filter that exists on that same column. KEEPFILTERS Replaces the override with an intersection. The test: put a slicer on Status_Group and choose Open only. Without KEEPFILTERS the measure will keep returning 35,487,304.63 and ignore the slicer; with KEEPFILTERS it will return empty — because the intersection of Open with Realized is an empty set. That's the correct answer.

Why this matters especially here: The third group, Lost, holds a collection zero but a charge of 10,410,534.43 dollars. The breakdown by status is exactly where the trap in the file is exposed to the eye.

result: 35,487,304.63 dollar.
By status group: Realized 35,487,304.63 · Open 14,806,752.24 · Lost 0.00

1.8 · % of All Programs — ALL releases the filter

Create a measure named % of All Programs that returns each plan's share out of all rows Dim_Program — even when the visual is filtered to one plan. Format as a percent with two decimal places.

% of All Programs =
DIVIDE (
  [Total Tuition Collected],
  CALCULATE (
    [Total Tuition Collected],
    ALL ( Dim_Program )
  )
)

Where ALL works: The numerator is calculated in row context — the tuition of the current program. The denominator is wrapped inCALCULATE with ALL ( Dim_Program ), which removes the filter on all the dimension's columns and always returns the total of all 24 programs. If you had written ALL ( Dim_Program[Program_Name] ) You'd only release one column — filter on Faculty_Name would keep truncating the denominator.

The sanity test: Drag the measure to the plans table. The percentage column must sum to exactly 100.00%. If it doesn't — that's a sign your denominator is filtered.

result: Public Health = 5.20% (2,613,332.23) · Digital Marketing = 2.88% (1,449,455.63) · column total = 100.00%

1.9 · Program Status — IF vs. a fixed target

Create a measure named Program Status that returns "Above Target" When the program's tuition reaches the annual target of 2,100,000 dollars, and"Below Target" otherwise.

Program Status =
IF (
  [Total Tuition Collected] >= 2100000,
  "Above Target",
  "Below Target"
)

A fixed target, not an average: The target here is a pre-agreed number set in the budget, not a value calculated from the data. The advantage: the result is stable and doesn't move when you filter the visual. The disadvantage: if you change the target you'll have to edit the formula — in exercise 2.6 you'll see how a What-if parameter solves this.

A text measure isn't a numeric measure: You cannot rank it, sum it, or feed it into a chart. Its place is in a table and a card only.

result: 14 Plans above target · 10 below it. The first program below the target: Social Work (1,995,665).

1.10 · Program Tier — SWITCH for three tiers

Create a measure named Program Tier that divides the plans into three tiers: "Top" from2,400,000 and above, "Mid" from1,900,000 and above, and the rest "Low". Use -SWITCH(TRUE()).

Program Tier =
SWITCH (
  TRUE (),
  [Total Tuition Collected] >= 2400000,
    "Top",
  [Total Tuition Collected] >= 1900000,
    "Mid",
  "Low"
)

Why SWITCH(TRUE()) and not nested IF: TRUE() as the first argument turns SWITCH into a list of conditions that are checked Top to bottom, and the first one that's true wins. Order is critical: had the Mid row come first, every program above 2.4 million would have gotten Mid, since they also pass the lower threshold.

The last argument without a condition It is the default. Without it, a row that does not meet any condition would return blank, and the visual would show an empty row instead of a label.

result: 6 Top plans · 13 Mid · 5 Low. 24 in total — each program received exactly one label.

1.11 · Tier Color — a SWITCH that returns a color

Create a measure named Tier Color that translates the [Program Tier] For the hex code: Top → #132449, Mid → #F5C518, and a default #A9B4CC. This is SWITCH on a value, not on TRUE().

Tier Color =
SWITCH (
  [Program Tier],
  "Top", "#132449",
  "Mid", "#F5C518",
  "#A9B4CC"
)

Two forms of the same function: In the previous exercise, SWITCH received TRUE() and compared conditions. Here it receives expression and compares it to values. This form is shorter and more readable when there's a closed list of values.

This measure is not meant to be seen. It feeds the conditional formatting pane in exercise 3.2. If you drag it into a table you'll see hex strings — that's expected.

result: 6 Plans receive #132449 · 13 receive #F5C518 · 5 receive #A9B4CC.

1.12 · Program Rank — dense RANK

Create a measure named Program Rank that ranks the programs by tuition charged, from highest to lowest, in a ranking crowded (DENSE).

Program Rank =
RANK (
  DENSE,
  ALLSELECTED (
    Dim_Program[Program_Name]
  ),
  ORDERBY (
    [Total Tuition Collected], DESC
  )
)

The three parts: DENSE Determines that after a tie the next rank is the next in line, not skipped · ALLSELECTED Defines the window — all the programs the slicer leaves visible · ORDERBY determines what to sort by. Without ORDERBY, RANK will sort by column order and return an alphabetical ranking.

Why ALLSELECTED and not ALL: with ALL The ranking would ignore the slicers and always range between 1 and 24. With ALLSELECTED Filtering to a single faculty re-ranks within that faculty — number 1 will be the leader within the current selection.

result: Public Health = 1 · Digital Marketing = 24. 24 programs, 24 rankings — there's no tie in this file, so DENSE and SKIP return the same thing here. The difference will show up once you filter to a faculty with identical values.

1.13 · Leader Tuition — INDEX returns the leader

Create a measure named Leader Tuition that returns, in every row, the tuition of the program the leader — the same number in every row of the table. UseINDEX with ORDERBY.

Leader Tuition =
CALCULATE (
  [Total Tuition Collected],
  INDEX (
    1,
    ALLSELECTED (
      Dim_Program[Program_Name]
    ),
    ORDERBY (
      [Total Tuition Collected], DESC
    )
  )
)

INDEX returns a row, not a number. It picks the row at the position you requested within the window — 1 = the first one after sorting. To turn a row into a number, wrap it inCALCULATE, that uses the selected row as a filter and runs the measure on it. INDEX ( -1, ... ) would return the last one.

What to do with it: A natural helper measure is DIVIDE ( [Total Tuition Collected], [Leader Tuition] ) — percent of the leader. For Public Health it will return 100%, and for Digital Marketing 55.46%.

result: 2,613,332.23 — the same number in all 24 rows. If it changes from row to row, your window isn't ALLSELECTED.

1.14 · Tuition Moving Avg 3M — WINDOW

Create a measure named Tuition Moving Avg 3M that returns a three-month moving average — the current month and the two months before it. UseWINDOW with REL.

Tuition Moving Avg 3M =
AVERAGEX (
  WINDOW (
    -2, REL, 0, REL,
    ALLSELECTED ( Dim_Date[Year_Month] ),
    ORDERBY ( Dim_Date[Year_Month], ASC )
  ),
  [Total Tuition Collected]
)

The first four numbers: -2, REL = lower bound, two rows back relative to the current row · 0, REL = upper bound, the current row itself. REL = relative to the current row; ABS It would count from the start of the window.

Why AVERAGEX and not AVERAGE: WINDOW returns table of up to three rows. AVERAGEX runs over it row by row, calculates the measure on each one, and only then averages. Switching toSUMX will give a running sum instead of a moving average.

The first two rows differ: In January 2023 there's one row in the window, and in February two, so the average there is of fewer than three months. This is correct behavior, not a bug — anyone who wants a blank in these rows must explicitly count them.

Display by Dim_Date[Year_Month] (36 months).
result: 2023-03 = 2,059,545.77 · 2025-12 = 1,593,617.98 (the month itself: 817,666.91 — the moving average softens the semester dip).

4.1 · The trap — explain why the naive answer is wrong

In this exercise, you don't write a measure. A fellow student built a measure Total Revenue = SUM ( Fact_Enrollments[Tuition_Billed_USD] ), got 61,236,519.19 dollars, and presents the number to management as "the institution's revenue". Write in three to four lines what exactly is wrong here, how big the gap is, and what check in the model would have exposed it within a minute.

The full answer — what is wrong: the column Tuition_Billed_USD documents charge, not collection. Two status groups out of three — Withdrawn andCancelled, which together are Status_Group = "Lost" — carry a positive charge and zero collection. The registration was cancelled, the money never came in, but the charge row remained in the fact table. A measure that sums up charges counts this money as if it were received.

How big is the gap: 61,236,519.19 less 50,294,056.87 = 10,942,462.32 dollars — 17.9% of total billing, all attributed to one group. The breakdown by status group: Realized 35,487,304.63 Billed and collected in full · Open 15,338,680.13 charged against 14,806,752.24 Charged · Lost 10,410,534.43 charged against 0.00 that was charged.

The check that reveals this in a minute: Build a Matrix with Dim_Status[Status_Group] in rows and two measures in values — total charged versus total collected. A row where one column is greater than zero and the other is zero is a red flag and impossible to miss. The general rule: Whenever two money columns in a working table look like twins, break both of them down by the status dimension before you choose one.

What was legitimate: Show the two numbers side by side and call them by name — "billed" and "collected" — and add a third measure for the gap. This turns the trap into an operational insight about the churn rate.
