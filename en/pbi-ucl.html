Champions League model — assignment prep and structure

Two dashboard pages where every number comes from a measure you write from scratch, with automatic color indication for club status. Working on UCL_PowerBI_Model.xlsx — a star schema with 32 tables, 100,000 rows and 44 relationships. 27 exercises, each on a separate page and with a full solution. Note: the download and practice are On the computer only — Power BI Desktop doesn't exist on phone.

The data is synthetic. The names of the clubs, stadiums, and cities are real, but every player, result, goal, and amount in the file were generated artificially. Nothing should be inferred from them about the real Champions League — and it's worth saying this explicitly to the class, because someone will always try to cross-check against their own memory.

Before we start — building the model. The file has 44 relationships; the assignment relies on ten of them. The table further down the page lists them one by one. Mark the Dim_Date As a date table (Mark as date table on Full_Date), turn off Autodetect and build manually, and make sure all relationships are in the direction Single From the dimension to the fact — the file has 11 fact tables that share dimensions, andBoth Produces a loop.

A gap that's not a bug: inDim_Date There are 4,383 dates, but the games table uses only 267 of them, and only 8 months a year. There are no games in January or June–August — those are the off-season months, and that's what creates the gaps in the line chart.

Matching brackets. Table[Column] = column · [measure] = square brackets without a table name. For each measure: right-click on Fact_PlayerMatchStats in the panel Data ← New measure ← the formula ← Enter.

1.1 · Total Goals — the base measure

Create a measure named Total Goals that summarizes the Fact_PlayerMatchStats[Goals]. Format with a thousands separator.

Total Goals = SUM ( Fact_PlayerMatchStats[Goals] )
  1. creationRight-click on Fact_PlayerMatchStats ← New measure
  2. checkDrag onto an empty card to make sure the number appears

The most important trap in this file: SUM ( Fact_Matches[Total_Goals] ) Returns 3,051 and not 2,970. The difference is 81 Own goals, credited to the opposing side but not attributed to any player — exactly like in real data. Both numbers are correct, they simply answer two different questions: "how many goals were scored in the matches" versus "how many goals players scored". This is a great exercise for showing why you have to define a metric before arguing about a number.

result: 2,970 Goals — the anchor number of the entire assignment.

1.2 · Matches Played — how many matches actually

Create a measure named Matches Played that counts games unique based on Fact_PlayerMatchStats[Match_ID].

Matches Played = DISTINCTCOUNT ( Fact_PlayerMatchStats[Match_ID] )

Why not COUNT: COUNT(Match_ID) would return 50,799 — it counts rows that have a value, not unique values. Every game is represented by 33 to 34 player rows (the roster of both teams), so 50,799 ÷ 1,500 ≈ 33.9.

result: 1,500 games.

1.3 · Goals per Match — the Lego principle

Create a measure named Goals per Match — strictly from the two existing measures, without the division sign / and without AVERAGE. Format to two decimal places.

Goals per Match = DIVIDE ( [Total Goals], [Matches Played] )

The average of what: AVERAGE(Fact_PlayerMatchStats[Goals]) would return 0.06 — an average per player-game row, not per game. When the measure is built from two existing measures, the denominator is explicitly defined and you know exactly what you divided. DIVIDE preferred over / because it returns blank instead of an error when the denominator is zero.

The measure automatically rolls up to any context: Drag it onto the clubs table and it will return the rate for each club separately — see the insight in exercise 2.4.

result: 1.98 Goals per game.

1.5 · Knockout Goals — first CALCULATE

Create a measure named Knockout Goals that returns the goals in the knockout stages only, with CALCULATE and a condition on Dim_Stage[Stage_Type].

Knockout Goals =
CALCULATE ( [Total Goals], Dim_Stage[Stage_Type] = "Knockout" )

What happens here: CALCULATE adds the condition to the filter bubble and only then runs the [Total Goals]. The filter sits on a text column in the dimension table, flows through the relationship to Fact_Matches and from there to the 50,799 fact rows — without any JOIN.

result: 671 — 22.59% of all goals. The breakdown by stage: Final 20 · Group Stage 2,299 · Quarter-Final 189 · Round of 16 370 · Semi-Final 92

1.6 · Home Goals — CALCULATE on another fact table

Create a measure named Home Goals that returns the goals of the home team. note: inFact_PlayerMatchStats There's no home/away column — it's in Fact_ClubMatchStats[Home_Away].

Home Goals =
CALCULATE (
    SUM ( Fact_ClubMatchStats[Goals_For] ),
    Fact_ClubMatchStats[Home_Away] = "Home"
)

Why not on the players table: The information simply doesn't exist there. It's in Fact_ClubMatchStats, with one row per team per game. Both measures live under the same slicers because both tables are connected to the same dimensions — and that's exactly what a good star schema gives you.

There's a real byte advantage here: 58.8% of goals go to the home team, and 44.2% of games ended in a home win (draw 28.5%, away win 27.3%).

Sanity check: 1,794 + 1,257 = 3,051. Note that the whole here is 3,051 and not 2,970, because this table does include own goals.

result: 1,794 — 58.8% (outside: 1,257).

1.7 · % of Competition Goals — ALL Releases the Filter

Create a measure named % of Competition Goals: Divide the [Total Goals] in the total goals of the whole competition — CALCULATE that removes the filter from Dim_Club using ALL. Format as a percentage, two digits.

% of Competition Goals =
DIVIDE (
    [Total Goals],
    CALCULATE ( [Total Goals], ALL ( Dim_Club ) )
)

What ALL does: The numerator lives in the row's bubble (one club), and the denominator is released from filtering and therefore always holds the entire competition. In the Total row the numerator already equals the denominator — and that's the check that the measure was written correctly.

Result: the leading club (Dynamo Kyiv) holds 3.16% · The Total row shows 100.00%.

1.8 · Club Status — IF vs. the competition average

Create a measure named Club Status that returns text: "above average" if the club scored 46 goals or more, and otherwise "below average".

Club Status =
IF ( [Total Goals] >= 46, "Above average", "Below average" )

Where does 46 come from: 2,970 ÷ 64 = 46.41 — average goals per club. The measure returns text, so it fits a table, not a numeric card.

Bonus question: Three clubs are tied at exactly 46 goals. Whoever writes > instead >= will get 27 instead of 30 — exactly the kind of mistake worth catching in class.

result: 30 Clubs "above average" · 34 "Below average".

1.9 · Club Tier — SWITCH for three tiers

Create a measure named Club Tier that classifies each club: "top" from 60 goals and up, "middle" from 40 and up, and otherwise "bottom". Use the template SWITCH ( TRUE (), … ).

Club Tier =
SWITCH (
    TRUE (),
    [Total Goals] >= 60, "Top",
    [Total Goals] >= 40, "Middle",
    "Bottom"
)

Order determines: SWITCH stops at the first condition that holds true. If ≥ 40 is written first, all top-tier clubs will be classified as "Middle" and the top tier will remain empty. The last argument, with no preceding condition, is the default.

result: 12 "top" · 31 "middle" · 21 "bottom".

1.10 · Tier Color — a SWITCH that returns a color

Create a measure named Tier Color That returns a HEX code by [Club Tier]: top #132449, middle #F5C518, default #A9B4CC. Here's the regular SWITCH pattern, without TRUE().

Tier Color =
SWITCH (
    [Club Tier],
    "Top", "#132449",
    "Middle", "#F5C518",
    "#A9B4CC"
)

The two forms of SWITCH side by side: In the previous exercise we used TRUE() because the conditions are range comparisons; here the expression is a text measure and the values are exact matches.

The common trap: SWITCH compares strings by exact match. One trailing space at the end of a string will fail silently, with no error message, and all the clubs will get the default color. Copy the strings from the previous measure, don't retype them.

The measure isn't shown in any visual — it's used only for the conditional formatting in exercise 3.2.

1.11 · Club Rank — RANK

Create a measure named Club Rank that ranks the clubs by [Total Goals] Using RANK on ALL ( Dim_Club[Club_Name] ), with ORDERBY in descending order. Requires Power BI from the 2023 version onward.

Club Rank =
RANK ( ALL ( Dim_Club[Club_Name] ), ORDERBY ( [Total Goals], DESC ) )

What ALL does: removes the row filter and returns all 64 clubs to the list of contenders — without it, in a single club's row there's a single contender and no one to rank.

What's different from RANKX: The default of ORDERBY is ASC, and therefore without DESC The weakest club will get rank 1 — the opposite of RANKX. In the Total row the function returns blank, because there's no "current row" to locate in the list.

result: Dynamo Kyiv = 1 · Lazio = 64.

1.12 · Leader Goals and % of Leader — INDEX

Create a measure named Leader Goals that returns in every row the goals of the first club in the list — CALCULATE with INDEX ( 1, … ). bonus: measure % of Leader — DIVIDE of the base measure by [Leader Goals], as a percent with one digit.

Leader Goals =
CALCULATE (
    [Total Goals],
    INDEX ( 1, ALL ( Dim_Club[Club_Name] ), ORDERBY ( [Total Goals], DESC ) )
)

% of Leader = DIVIDE ( [Total Goals], [Leader Goals] )
A fixed money column — the leader's value repeats on every row

1.13 · Running Goals — WINDOW

Create a measure named Running Goals — a running total from the start of the list to the current row, using WINDOW ( 1, ABS, 0, REL, … ) With the same ALL and the same ORDERBY.

Running Goals =
CALCULATE (
    [Total Goals],
    WINDOW ( 1, ABS, 0, REL,
        ALL ( Dim_Club[Club_Name] ),
        ORDERBY ( [Total Goals], DESC )
    )
)
The window grows row by row up to the competition total
clubTotal GoalsRunning Goals
Dynamo Kyiv9494
Liverpool FC78172
Celtic FC77249

Athletic Club162,957

The logic of the four numbers: 1, ABS = starting at position 1 absolute, the head of the list · 0, REL = stop 0 steps from me, meaning at my own position. If you replace with1, ABS ← 3, ABS You'll get a fixed column with the sum of the top three — one word turns a moving window into a fixed window.

A built-in sanity check: the last row must be exactly 2,970. If not, something in the window is broken.

1.14 · Total Attendance — the third fact table

Create a measure named Total Attendance that summarizes the Fact_Matches[Attendance]. Format with Display units = Millions anddecimal places = 1.

Total Attendance = SUM ( Fact_Matches[Attendance] )

Why this matters: The measure proves that the model connects three fact tables under the same slicers. Select a season in the slicer — goals, assists, and attendance will update together.

3.2 · Field value — the SWITCH measure feeds the color

Color the clubs table (exercise 2.7) without writing a single rule by hand — the color comes from the measure Tier Color you wrote in exercise 1.10.

Format visual <- Cell elements
  Series: Club Tier
  Background color = On <- fx
  Format style = Field value
  What field should we base this on? = [Tier Color]

Why this is stronger than Rules: The rules in exercise 3.1 live inside a single visual — changing the threshold requires fixing every visual separately. The measure Tier Color is a single source of truth: One change in the SWITCH code updates everywhere it is used.

If the text can't be read on the dark background — also turn on Font color the same way with your own color-text measure.

Both techniques produce exactly the same split: 12 / 31 / 21.
