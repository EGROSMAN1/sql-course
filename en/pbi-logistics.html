The data is synthetic. The city and country names are real, but every customer, carrier, shipment, and number in the file was generated artificially with a fixed random seed. Nothing about the real shipping market should be inferred from them.

Before we start — building the model. The file has exactly seven relationships, all from the dimension to the fact table. Mark Dim_Date As a date table (Mark as date table on Full_Date), turn off Autodetect and built manually, make sure every relationship is One to many in the direction Single from the dimension to Fact_Shipments. Sheet Relationships The file lists the seven relationships one by one. There's no dimension-to-dimension relationship and no bridge table — every dimension touches the facts directly, and only them.

The big trap in this file. in the table of Dim_Carrier there is 12 leaders, but the fact table only shows 11. the row Danube Barge Union it A dimension row that no fact row points to. The practical, immediate meaning: a visual showing leaders will show 11 rows and not 12, because Power BI hides dimension values with no data by default; COUNTROWS ( Dim_Carrier ) will return 12 while DISTINCTCOUNT ( Fact_Shipments[Carrier_ID] ) will return 11; and in every window function that relies on ALLSELECTED ( Dim_Carrier[Carrier_Name] ) A blank row twelve will appear and will throw off the ranking, median, and cumulative percent if you do not filter it out. The two small traps: column Revenue_Per_KG_USD it's a ratio and must not be summed, and rows Cancelled andReturned carry unrealized revenue.

Matching brackets. Table[Column] = column · [measure] = square brackets without a table name. For each measure: right-click on Fact_Shipments in the panel Data ← New measure ← the formula ← Enter. The name must be exactly as it appears in the exercise, otherwise measures built on it won't find it.

1.5 · Revenue per KG — the Lego principle

Create a measure named Revenue per KG — using only the two existing measures, without the division symbol / and without AVERAGE. Format to four digits.

Revenue per KG =
DIVIDE (
    [Total Freight Revenue],
    [Total Weight Shipped]
)

Why DIVIDE and not /: If the denominator comes out zero or blank — and a customer with no shipments in a given context is exactly such a case — the / operator returns an error that stains the entire visual, whereas DIVIDE Silently returns empty.

and why from two measures and not columns: When the measure is built from two existing measures, it accounts for the filter context in each cell individually and recalculates the numerator and the denominator. In exercise 1.15 we'll see exactly what happens when you try to take a shortcut.

result: 0.3156 Dollars per kg (8,466,765.26 partial 26,825,847.8).

1.7 · On Time Delivered Revenue — Two Conditions with &&

Create a measure named On Time Delivered Revenue That returns the revenue of shipments that were both delivered and arrived on time: Shipment_Status = "Delivered" and also On_Time_Status = "On_Time". You must use && inside a single condition, not two separate filters.

On Time Delivered Revenue =
VAR Ok =
    FILTER (
        Fact_Shipments,
        Fact_Shipments[Shipment_Status]
            = "Delivered"
        && Fact_Shipments[On_Time_Status]
            = "On_Time"
    )
RETURN
CALCULATE ( [Total Freight Revenue], Ok )

Why FILTER and not two boolean filters: Two separate filters in CALCULATE intersect and return exactly the same result here — but the exercise asks for one combined condition, and that's what && gives. The real difference shows up when you want or instead and also: the || It can't be expressed with two separate filters, and only FILTER will allow it.

The cost of FILTER: it scans the fact table row by row. For 28,400 rows it's not noticeable, on ten million it is. The rule: boolean filter when possible, FILTER when necessary.

result: 5,159,284.25 dollar — 69.31% of the revenue given.

1.8 · Pct of Grand Total — ALL on two dimensions

Create a measure named Pct of Grand Total that returns each cell's share of the total, with the denominator freed from any filter of second Dimensions all at once — Dim_Carrier andDim_Service_Level. Format as a percent.

Pct of Grand Total =
VAR Grand =
    CALCULATE (
        [Total Freight Revenue],
        ALL ( Dim_Carrier ),
        ALL ( Dim_Service_Level )

RETURN

        [Total Freight Revenue],

Why ALL on the table and not on the column: ALL ( Dim_Carrier ) Neutralizes all dimension columns at once — also Carrier_Name and also Carrier_Mode and also Contract_Tier. 1.9 · Revenue vs Prev Month — IF against the previous period

Create a measure named Revenue vs Prev Month That returns the string Up If revenue in the current month is greater than or equal to revenue in the previous month, and otherwise Down. Use two VAR variables.

Revenue vs Prev Month =
VAR Cur = [Total Freight Revenue]
VAR Prev =
    CALCULATE (
        [Total Freight Revenue],
        DATEADD (
            Dim_Date[Full_Date],
            -1,
            MONTH
        )
    )
RETURN
    IF ( Cur >= Prev, "Up", "Down" )

Why this only works after Mark as date table: DATEADD It's a time-intelligence function, and it requires a continuous, marked date table. Dim_Date contains 731 Consecutive days without a single gap — this isn't accidental, it's the requirement.

and why not subtract the previous month manually: Month_Number - 1 breaks in January. DATEADD knows how to cross a year.

1.10 · Margin Tier — SWITCH ( TRUE () )

Create a measure named Margin Tier that classifies each carrier by its gross margin percentage into three tiers: Leader From 20% and up, Challenger From 12% and up, and everything else Laggard. Use SWITCH with TRUE.

Margin Tier =
VAR TotMargin =
    SUM (
        Fact_Shipments[Gross_Margin_USD]
    )
VAR MarginPct =
    DIVIDE (
        TotMargin,
        [Total Freight Revenue]
    )
RETURN
    SWITCH (
        TRUE (),
        MarginPct >= 0.20, "Leader",
        MarginPct >= 0.12, "Challenger",
        "Laggard"
    )

Why SWITCH ( TRUE () ) and not nested IF: A nested IF at three levels is still readable, at six it's not anymore. SWITCH with TRUE keeps one column of conditions checked top to bottom, and the first one that's true wins — so Order is critical: if you put the 12% threshold first, every carrier above 20% will be classified as Challenger and none will reach Leader.

1.12 · Carrier Rank by Shipments — RANK by quantity

Create a measure named Carrier Rank by Shipments that ranks the leaders by Number of shipments — not by income. Skip ranking (SKIP), from highest to lowest, with an explicit ORDERBY.

Carrier Rank by Shipments =
RANK (
    SKIP,
    ALLSELECTED (
        Dim_Carrier[Carrier_Name]
    ),
    ORDERBY (
        COUNTROWS ( Fact_Shipments ),
        DESC
    )
)

Why ALLSELECTED and not ALL: ALL It would also ignore slicers the user selected, and the ranking would always be against all 12 leaders. ALLSELECTED Neutralizes only the filter that the visual itself creates, and respects the slicers — so if the user filters to three leaders, the ranking runs 1 to 3.

and here we run into the trap. ALLSELECTED ( Dim_Carrier[Carrier_Name] ) returns 12 Names — including Danube Barge Union that has no fact row at all. COUNTROWS ( Fact_Shipments ) returns blank for it, and RANK's default (KEEP) pushes blanks to the end. So the last rank in the table will be 12 and not 11 — and if you activate Show items with no data You'll see it on the screen.

1.13 · Median Carrier Revenue — INDEX on the Median Value

Create a measure named Median Carrier Revenue that returns the leader's revenue the median — not the average and not the leader. Use INDEX with ascending ORDERBY, and first filter out leaders with no data.

Median Carrier Revenue =
VAR Carriers =
    FILTER (
        ALLSELECTED (
            Dim_Carrier[Carrier_Name]
        ),
        NOT ISBLANK (
            [Total Freight Revenue]
        )
    )
VAR MidPos =
    ROUNDUP (
        COUNTROWS ( Carriers ) / 2,
        0
    )
RETURN
    CALCULATE (
        [Total Freight Revenue],
        INDEX (
            MidPos,
            Carriers,
            ORDERBY (
                [Total Freight Revenue],
                ASC
            )
        )
    )

Why FILTER on NOT ISBLANK: Without this row COUNTROWS ( Carriers ) would return 12 instead 11, MidPos would have come out 6 out of 12 — and that's no longer the median but the sixth item in a list whose first entry is empty. The file's trap shifts the result by an entire row.

Why ROUNDUP and not ROUND: in11 items, the median is the sixth item — 11 partial 2 it 5.5, and only rounding up gives 6. Regular rounding would give 6 Also, but in13 items (6.5) it would have given 6 instead 7.

What INDEX returns: not a number but row. That's why it sits as a filter argument inside CALCULATE, and not as a value returned directly.

result: 646,970.08 dollars — Channel Sea Lines, position6 out of 11 in ascending sort. An independent check in pandas on the same 11 gives values 646,970.08 — identical.

1.14 · Cumulative Pct of Revenue — a cumulative WINDOW in percent

Create a measure named Cumulative Pct of Revenue which returns the cumulative percentage of revenue, with the leaders sorted from largest to smallest. Use WINDOW from the very first row to the current row.

Cumulative Pct of Revenue =
VAR RunTotal =
    CALCULATE (
        [Total Freight Revenue],
        WINDOW (
            1, ABS,
            0, REL,
            ALLSELECTED (
                Dim_Carrier[Carrier_Name]
            ),
            ORDERBY (
                [Total Freight Revenue],
                DESC
            )
        )
    )
VAR AllCarriers =
    CALCULATE (
        [Total Freight Revenue],
        ALLSELECTED (
            Dim_Carrier[Carrier_Name]
        )
    )
RETURN
    DIVIDE ( RunTotal, AllCarriers )

to read the four numbers: 1, ABS = start at the very first row of the whole list, regardless of the current position. 0, REL = ends at the current row (0 rows from it). This is exactly the definition of a cumulative window. If you had written -2, REL instead 1, ABS, you would get a sliding window of three rows instead of accumulation.

Why two VARs and not one: The numerator is the sum of the window and the denominator is the total of that same list. Both use the same ALLSELECTED — and that's what guarantees the last percentage is exactly 100 and not 99.7.

1.15 · Explanation exercise — why the shortcut in the ratio column is wrong

In this exercise, you don't write a measure. A student looked at Fact_Shipments[Revenue_Per_KG_USD], saw that it already computes revenue per kg in every row, and instead of Exercise 1.5 wrote this:

Naive Revenue per KG =
AVERAGE (
    Fact_Shipments[Revenue_Per_KG_USD]
)

Its result: 0.3815. The correct result from exercise 1.5: 0.3156. The gap is 20.9%. Explain in your own words why his measure is wrong, not just different. Answer before opening.

The answer: the average of ratios is not the ratio of averages. Revenue_Per_KG_USD It is a ratio column — numerator over denominator at the row level. When you compute AVERAGE on it, every shipment gets equal weight: a shipment of 30 kg affects the result exactly like a shipment of 20,000 kg.

and why it tilts upward specifically: In this file, revenue is built from a fixed component per shipment plus a component based on weight. Small shipments carry the same fixed component over very little weight, so their ratio is very high. They're numerous and light — so a simple average, which counts shipments, is inflated compared to a calculation weighted by kg.

When is it still allowed to sum a derived column: whenSUM equals applying the formula to the totals. Gross_Margin_USD Passes the test — the sum of the differences equals the difference of the sums, and therefore SUM ( Gross_Margin_USD ) Completely valid. Revenue_Per_KG_USD fails, and also its sum (10,834.60) is a meaningless number.

The rule to remember: Addition and subtraction pass through the schema, multiplication and division don't. Any column that's a ratio, percentage or average — you only touch it through a measure that recalculates from the numerator and denominator.

There's no measure to check here. The check is that you explained two things: that the weight in a simple average is the number of shipments, not the number of kg, and that the test is whether the summing happens through the operation.

3.2 · The exact same split, using the Rules method

They arrived at exactly the same split — but without a color measure. They usedRules on the margin percentage. The goal: to prove to yourself that both approaches produce an identical result, and understand when each is preferable.

First create a helper measure for the gap vs. the target:

Margin Gap vs Target =
VAR TotMargin =
    SUM (
        Fact_Shipments[Gross_Margin_USD]
    )
VAR Pct =
    DIVIDE (
        TotMargin,
        [Total Freight Revenue]
    )
RETURN Pct - 0.18
  1. openingCell elements ← Background color ← fx
  2. methodFormat style ← Rules
  3. baseWhat field should we base this on ← Margin Gap vs Target
  4. rule 1If value ≥ 0.02 ← #132449
  5. rule 2If value ≥ -0.06 ← #F5C518
  6. rule 3If value < -0.06 ← #A9B4CC

Why the thresholds look different: The measure returns a gap against an 18% target, so a 20% threshold becomes+0.02 and a threshold of 12% becomes-0.06. Same division, a different reference point.

The trap of Rules: Percent against Number in the menu. If you leave Percent, Power BI will interpret the thresholds as a percentile of the range rather than as a value — and the split will come out completely different. Choose Number.

When Rules is preferable anyway: When the logic belongs to a single visual only, when you need a continuous scale instead of three tiers, or when you're not allowed to create additional measures in the model.

Result: the exact same division — 5 / 4 / 2. If you get something else, check the Number against Percent.
