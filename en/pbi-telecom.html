The data is synthetic. The country names are real, but every customer, package, device, channel and number in the file was artificially generated with a fixed random seed 20260821. Nothing about the real telecom market should be inferred from them.

Before we start — building the model. The file is a pure star schema: a single fact table Fact_Usage and seven dimensions, and every dimension connects directly to it. There's no dimension-to-dimension relationship and no concatenation. Mark Dim_Date As a date table (Mark as date table on Full_Date), turn off Autodetect and build the seven relationships manually, all of them Single From the dimension to the fact. Both here is completely unnecessary.

The trap of this file — rows with intentionally negative spacing. in the table of Fact_Usage there is 2,824 rows (9.41%) where Gross_Margin_USD negative — subsidized devices and roaming packages bought at a wholesale cost higher than the price to the customer. They carry 241,146.59 USD revenue and delete 50,484.13 USD margin. A total-margin measure silently offsets them and shows 889,705.65 instead 940,189.78. The loss doesn't disappear — it just hides in the schema. Exercise 3.3 breaks it down.

A column that looks additive but isn't. Fact_Usage[Revenue_Per_GB] It's a ratio, not a sum. Dragging it with Sum returns 1,374,449.63 — a number with no meaning at all. Exercise 3.2 explains exactly why, and what to do instead.

Matching brackets. Table[Column] = column · [measure] = square brackets without a table name. For each measure: right-click on Fact_Usage in the panel Data ← New measure ← the formula ← Enter. The name must be exactly as it appears in the exercise.

1.1 · Total Billed Revenue — the anchor measure

Create a measure named Total Billed Revenue that summarizes the Fact_Usage[Billed_Amount_USD]. Format with a thousands separator and two decimal digits.

Total Billed Revenue =
SUM ( Fact_Usage[Billed_Amount_USD] )
  1. creationRight-click on Fact_Usage ← New measure
  2. designFormat ← Currency ← two digits
  3. checkDrag onto an empty card to make sure the number appears

Why this is a measure and not a column: A calculated column would be stored once per row out of 30,000 and wouldn't know how to respond to a slicer. A measure is recalculated at every cell of every visual, according to the filter bubble that cell represents. That's the only difference that really matters.

result: 2,594,253.85 USD — the anchor number of the whole assignment.

1.2 · Total Gross Margin — the second SUM

Create a measure named Total Gross Margin that summarizes the Fact_Usage[Gross_Margin_USD]. Note that this is a column otherwise than that of exercise 1.1.

Total Gross Margin =
SUM ( Fact_Usage[Gross_Margin_USD] )

The column is derived, not invented: Gross_Margin_USD = Billed_Amount_USD - Service_Cost_USD in each of the 30,000 rows. Therefore 2,594,253.85 less 1,704,548.20 Exactly equal 889,705.65. If you get something different — the load broke something, not the model.

Early warning: This total margin already offsets within it 2,824 loss rows. Exercise 3.3 breaks them down.

result: 889,705.65 USD — 34.3% from the income.

1.3 · Active Customers — how many customers, really

Create a measure named Active Customers that counts customers unique based on Fact_Usage[Customer_ID].

Active Customers =
DISTINCTCOUNT ( Fact_Usage[Customer_ID] )

Why not COUNT: COUNT(Customer_ID) would return 30,000 — it counts rows that have a value, not distinct values. Every customer carries 24.3 usage rows in the average, so 30,000 ÷ 1,236 ≈ 24.3.

result: 1,236 Active customers.

2.4 · Devices In Use — the second DISTINCTCOUNT

Create a measure named Devices In Use that counts unique device models based on Fact_Usage[Device_ID] — a different column than exercise 1.3's. The measure serves the Treemap in exercise 2.10.

Devices In Use =
DISTINCTCOUNT ( Fact_Usage[Device_ID] )

Note the level of detail: The measure counts models, not physical units. Dim_Device contains 48 Models and everyone appear in the fact table, so at the grand-total level the measure returns exactly the number of rows in the dimension. As soon as you filter a region or period the number drops — and that's exactly what makes it a useful measure.

result: 48 Device models.

1.5 · Revenue per Customer — the Lego principle

Create a measure named Revenue per Customer — strictly from the two existing measures, without the division sign / and without AVERAGE. Format to two decimal places.

Revenue per Customer =
DIVIDE ( [Total Billed Revenue],
         [Active Customers] )

The average of what: AVERAGE(Billed_Amount_USD) would return the average for a usage row (86.48 USD), not per customer. When the measure is built from two existing measures the denominator is defined explicitly and you know exactly what you divided. DIVIDE Preferable to / because it returns blank instead of an error when the denominator is zero.

The measure automatically rolls up to any context: Drag it onto the regions table and it will return the ARPU of each region separately — without writing another line.

result: 2,098.91 USD per customer.

Postpaid Revenue =

1.7 · Core Services Revenue — CALCULATE with IN

Create a measure named Core Services Revenue that returns the revenue from just three core services: Mobile Data, Fiber Broadband andIPTV. Use the operator IN { } and not in three OR conditions.

Core Services Revenue =
CALCULATE (
    [Total Billed Revenue],
    Dim_Service_Type[Service_Name] IN {
        "Mobile Data",
        "Fiber Broadband",
        "IPTV"
    }
)

Why IN and not OR: Three conditions || work on the same column, but they expand into three separate filters that the engine has to unify. IN { } produces a single list of values — shorter, faster, and easy to add a fourth value to without touching the logic.

The trap with curly braces: { } In DAX it’s a table constructor, not a list. If you write a value there that doesn’t exist in the column — you won’t get an error, you’ll simply get less revenue. Check the spelling against Dim_Service_Type before you blame the measure.

1.8 · Pct of All Usage — ALL and percent of all facts

Create a measure named Pct of All Usage that returns the current row's share out of all the revenue in the fact table. Display it in a table by Dim_Service_Type[Service_Name] and check that the column sums to 100%.

Pct of All Usage =
DIVIDE (
    [Total Billed Revenue],
    CALCULATE (
        [Total Billed Revenue],
        ALL ( Fact_Usage ),
        ALL ( Dim_Service_Type )
    )
)

Why two ALLs and not one — that's the point of the exercise: ALL ( Fact_Usage ) Clears filters sitting on fact table columns. It no Clears a filter that came fromDim_Service_Type and flows in through the relationship. If you leave only the first-ALL — the numerator and denominator will be identical in every row and the measure will return 100.00% in every row — and this is the most common mistake with this measure.

Immediate sanity check: If the sum of the column in the table isn't exactly 100.00% — the denominator wasn't really released. That's the only check you need.

1.9 · Margin Status — IF against a computed break-even point

Create a text measure named Margin Status that compares revenue to the break-even point — that is, to the cost of service in the same context — and returns Above Break-Even or Below Break-Even. The break-even point must be calculated inside the measure, not a hardcoded number.

Margin Status =
VAR BreakEven =
    SUM ( Fact_Usage[Service_Cost_USD] )
VAR Revenue = [Total Billed Revenue]
RETURN
IF (
    Revenue >= BreakEven,
    "Above Break-Even",
    "Below Break-Even"
)

Why VAR and not writing the sum twice: VAR is calculated once per cell and then reused. It's both faster and prevents the classic mistake where someone changes the formula in one place and forgets the other.

The break-even point shifts with the context: At the grand total level it is 1,704,548.20 USD, and in every service row it's the cost of only that service. This is exactly the difference between a measure and a hardcoded number — a hardcoded number would mark everything as profitable or everything as a loss.

1.10 · Region Tier — SWITCH ( TRUE ( ) )

Create a measure named Region Tier that divides regions into three tiers by revenue: Top From 250,000 USD and up, Mid From 150,000 and up, and everything else Low. Use SWITCH ( TRUE ( ) ) and not a nested IF.

Region Tier =
VAR Revenue = [Total Billed Revenue]
RETURN
SWITCH (
    TRUE (),
    Revenue >= 250000, "Top",
    Revenue >= 150000, "Mid",
    "Low"
)

Why SWITCH ( TRUE ( ) ): It reads the conditions top to bottom and stops at the first one that's true, exactly like a nested IF — but without the nesting. Adding a fourth layer is one line, not re-parsing parentheses.

The order is the logic: If you flip the two rows and put 150000 First, every region above 250,000 will get Mid — because it also satisfies the looser condition. There's no error, just a silent, wrong result.

Create a measure named Tier Color That receives the result of [Region Tier] and returns a hash code: Top ← #132449, Mid ← #F5C518, everything else ← #A9B4CC. This is a SWITCH on value, not on TRUE ( ).

Tier Color =
SWITCH (
    [Region Tier],
    "Top", "#132449",

Two forms of the same function: In 1.10 the first argument was TRUE () and each pair was a condition-and-result. Here the first argument is an expression, and each pair is a value-and-result - a simple equality comparison. The last, unpaired argument is always the default.

1.12 · Region Rank by Customers — RANK

Create a measure named Region Rank by Customers That ranks regions by Number of customers (not by revenue), from high to low, in dense ranking. Use RANK with ORDERBY.

Region Rank by Customers =
RANK (
    DENSE,
    ALLSELECTED ( Dim_Region ),
    ORDERBY ( [Active Customers], DESC )
)

The three parts of RANK: DENSE Ensures there are no gaps in the numbering, ALLSELECTED ( Dim_Region ) defines the comparison group — all the regions the slicer left on screen — andORDERBY Determines what to sort by. Without the second argument, every row will rank itself against itself and get 1.

Why ALLSELECTED and not ALL: ALL It would also ignore the slicer, so a region filtered out would still take up a spot in the ranking. ALLSELECTED Ranks within what the user actually sees — and that's almost always what you want in a dashboard.

1.13 · Top Margin Channel Rev — INDEX

Create a measure named Top Margin Channel Rev that returns the revenue of the channel with The highest margin — the same number in every row of the table, so it can be compared against. Use INDEX with ORDERBY.

Top Margin Channel Rev =
VAR TopRow =
    INDEX (
        1,
        ALLSELECTED ( Dim_Channel ),
        ORDERBY (
            [Total Gross Margin], DESC
        )
    )
RETURN
CALCULATE (
    [Total Billed Revenue],
    TopRow
)

INDEX returns a row, not a number: INDEX ( 1, ... ) It picks the first row in the sort you defined and returns a single-row table. To get a number from it you need to feed it as a filter into CALCULATE - which is why the measure is built in two steps.

The sort is by interval, the output is revenue: And that's exactly the point. The channel leading by a margin is Web Self Service with 203,233.89 USD margin, while the channel that leads in revenue is Authorised Dealer with 518,340.19 USD. Two different leaders — exercise 3.4 comes back to this.

1.14 · Trailing Avg Excl Current — WINDOW

Create a measure named Trailing Avg Excl Current that returns the average revenue of The three months preceding for the current month — without including the current month itself. Use WINDOW with ORDERBY on Dim_Date[Month_Key].

Trailing Avg Excl Current =
AVERAGEX (
  WINDOW (
    -3, REL, -1, REL,
    ALLSELECTED ( Dim_Date[Month_Key] ),
    ORDERBY ( Dim_Date[Month_Key], ASC )
  ),
  [Total Billed Revenue]
)

Reading the boundaries: -3, REL it is three rows back from the current row, -1, REL it's one row back. The window stops before the current month, so the average doesn't include it. If you write 0, REL At the upper bound — you got a regular four-month moving average, and that's a different exercise.

Why Month_Key and not Month_Label: WINDOW sorts the rows by the column you gave to ORDERBY, and it must be the same column that appears on the visual's axis. Month_Key it's a number (202401) so it also sorts correctly across years. Put it on the axis.

The first month returns empty: There are no rows before it, and the window is empty. This is correct, not a bug — don't wrap it inCOALESCE Just to see zero.

3.2 · Why the naive answer is wrong — and not writing a measure

This exercise does not ask for a measure. A manager asks, "How much do we charge on average per GB?". An analyst drags the Fact_Usage[Revenue_Per_GB] to the card, choose Average and gets 45.8150 USD. The correct answer is 1.2057 USD — times 38.0 less. Write in two-three lines why the naive approach is wrong, and what to do instead.

The answer: the average of ratios is not the ratio of the sums. Revenue_Per_GB calculated for each row separately — Billed_Amount_USD / Data_Volume_GB — and therefore a row that consumed 0.03 GBP and paid 6.00 USD contributes a ratio of 200 Just like a row that consumed 400 etc. AVERAGE gives both of them equal weight, and the small rows — which are the majority — pull the result up.

What to do instead: Calculate the ratio once at the aggregate level, don't average ratios:

True Revenue per GB =
DIVIDE (
    [Total Billed Revenue],
    SUM ( Fact_Usage[Data_Volume_GB] )
)

and why the column shouldn't be summed at all: SUM(Revenue_Per_GB) returns 1,374,449.63 — a number that has no unit and no meaning. Any column that has already been divided isn't additive, so it needs to be hidden in the model (Hide in report view) so no one drags it by mistake.

calculationresultvalid?

SUM ( Revenue_Per_GB )1,374,449.63No — a non-additive column

The correct answer: 1.2057 USD to GBP (2,594,253.85 ÷ 2,151,653.92 etc.).
