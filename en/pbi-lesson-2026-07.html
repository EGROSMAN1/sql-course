Chapter I · Why the browser

The pain that gave birth to the transition

Before the features — the architectural problem they come to solve.

Until now, any change to the model — even renaming a column, even fixing a relationship — required a whole route: download the pbix file, open Desktop on Windows, edit, republish, and hope no one else touched the model in the meantime. This locks out Mac users entirely, prevents two people from working in parallel, and drags a full publish cycle into a two-minute fix.

01

The main problem

The pbix file is a monolithic artifact. As long as the model lives in a binary file on someone's computer — there's no governance, no real version control and no collaboration.

02

the vision

The semantic model is a service, not a file. The browser is the client, TMDL is the format, and Git is the source of truth.

03

the price

Two editing surfaces for the same model create two versions of the truth. Chapter IV in the lesson is entirely about this cost.

Power BI Desktop doesn't disappear — but it becomes one tool among several, instead of the only gateway to the model.

Chapter II · TMDL — The Model as Code

What is TMDL and the workflow

Once you understand that the model is text, mass changes stop being a problem.

TMDL, short for Tabular Model Definition Language, is the textual representation of the semantic model. Every table, column, measure, relationship and perspective is text.

  1. ScriptDrag an object from the data panel to the editor, or right-click and choose Script TMDL. You can drag an entire section, and select several objects with CTRL.
  2. EditThe editor includes semantic highlighting, autocomplete (also with Ctrl+Space), tooltips, code actions with a lightbulb, formatting with Shift+Alt+F, and a Problems panel.
  3. PreviewShows a full diff of the model before and after running the script, in red and green.
  4. ApplyRuns the script against the model. On failure, an Output pane opens with the error details.
Two subtleties in Preview: The comparison isn't against the script in the tab but a comprehensive model comparison, so some properties may appear in a different order. In addition — preview only runs on valid TMDL; a faulty script won't run a preview at all.
TMDL only touches metadata: A change doesn't refresh the data and doesn't affect the report. If you changed a Power Query expression or a calculated column — you must refresh manually.

Chapter II · TMDL — The Model as Code

Renaming and sourceColumn

The real power of TMDL, and the minutes nobody tells you about.

Renaming an object requires writing a script of the father its: renaming a column requires the table's script, and renaming a table requires the script of the whole model. After that, find and replace with regular expressions does the job.

Field in the dialogthe value
Find(^\s+column\s+)(.+)
Replace$1\L$2

To convert all the column names in the table to lowercase. Make sure Regular Expression is turned on, then Replace All and Apply

The least intuitive trap in the lesson: After renaming in TMDL, the column name will differ from the property sourceColumn. The sync between the model table and the Power Query query is based on sourceColumn, so the names stay independent: the Power Query editor will display the sourceColumn names, and renaming through the interface will not add a rename step to the query as long as the two are not identical.
✓ Before every Apply: run Preview and scan the diff — to make sure you haven't touched measure or column names that contain the same string. And after Apply — check the dependent reports, because renaming a field can break visuals.

Chapter III · Model Options in the service

The settings and validity timing

What used to be locked in Desktop opens up in the browser — with different timing for each setting.

Why Microsoft introduced this

These settings determine fundamental behavior of the model: whether hidden date tables get created, how dates and numbers are parsed, how many parallel connections open to the source. Until now they were locked in Desktop, so even someone managing the model in the service was blind to them. The result: models bloated with unnecessary date tables without anyone noticing.

How to get there

Open a semantic model in Model view in the service, switch to Editing mode, and then File > Options. Write permission is required.

Chapter III · Model Options in the service

The three traps of the dialog

One setting in the browser can break dozens of downstream reports.

Turning off Auto date/time is a destructive action: Turning it off deletes the hidden date tables behind the automatic date hierarchies. Reports that use them will show broken-field errors after the refresh. The immediate fix — turn it back on; the permanent fix — switch to an explicit date table.
A Locale trap with no way back: Some locales aren't displayed correctly in the dialog and may appear empty. The model keeps working, but if you change the locale in this state — it can't be reverted in the browser, and you have to republish from Desktop.
limitationthe implication
Per model onlyThere are no defaults for new models and no bulk update in the browser
Only from Model viewThe dialog isn't available from Report view, from DAX Query View, from TMDL View, or from the settings page
Save failedmake sure there are no concurrent changes via XMLA or another client, close and reopen the dialog, and try again
Chapter IV · Sync and override

The override scenario — why it happens

The most important topic in the lesson. It's not a bug, it's architecture.

the principle: Publishing from Desktop is an operation of Full replacement of the model, not a merge. Desktop does not know what happened in the service since the download, so it writes its own snapshot over everything.

Desktop settings are saved on publish, so the initial values in the browser reflect what was in Desktop. Once you change a setting in the service, the service's values take precedence. But if you download the pbix, edit it in Desktop, and republish — the Desktop settings overwrite the service's values, and any change made in the service between the download and the publish is lost. Changes in the service do not sync back to the local file.

TIMELINE
Sun 09:00 download the pbix from the service
Sunday 11:00 Amit adds a measure in the browser and changes Locale
Monday 14:00 the pbix from Sunday gets republished
              ← Amit's measure and Locale disappeared
✓ The only rule that prevents this: One source of truth per model. Don't mix editing in Desktop with editing in the browser on the same model.

The distribution pain

One organization, different audiences: management wants three metrics, regional managers want a full breakdown, analysts want everything. The solution was to duplicate — another workspace, another app, another copy of the same report.

03

Chapter V · Enterprise apps with audiences

Permissions and lifecycle

The change that really matters is here, not in the interface.

Access distribution applies both to the items and to the semantic models behind them. Removing a user or removing content consistently revokes access, and no dangling access to models is left behind. This is secure-by-default behavior, which eliminates a familiar source of confusion from workspace apps.

The life cycle

  • ✓The items are pulled directly from the workspace content, and updates flow to them automatically
  • ✓You can do staging and controlled promotion via deployment pipelines or Git
  • ✓API-Full APIs for creating, reading, updating, deleting and listing — for app items and for audience items as child items
  • ✓In July, equivalent APIs were also added for Paginated Reports
An operational implication that's easy to miss: Since item updates flow automatically, there's no longer an "app publish" step acting as a gate. Editing a report in the production workspace is a change in production. Anyone who wants a control gate needs deployment pipelines or Git.

Priority order in design

The theme comes out of the JSON file and goes into the Format pane.

When the preview is on and no visual is selected, the format pane shows the theme settings. The change applies immediately to the whole report.

the segmentWhat can be changed

The priority order you must understand: Formatting applied manually to a single visual takes precedence always on the theme. So changing the theme will only update visuals that were left with the default formatting — which is why an old report "doesn’t respond" to a branding change.
Warning before resetting: Reset to default on an entire visual also removes button actions, conditional formatting rules, images from a URL or a field, and attribution labels. It's better to reset a single section in the formatting pane.
Chapter VI · Themes and Mobile

Mobile — the report on a small screen

A mobile layout isn't a shrunk desktop, it's a different report.

How it works: A mobile-optimized view is displayed only In the iOS and Android apps, and only in portrait mode. In the browser the report is always shown in the regular layout. Built in View > Mobile layout in Desktop, or via editing the report in the service.
  1. Building both layouts togetherDuplicating a page duplicates both, so a page with a title and navigation serves as a template for the other pages.
  2. Select only what mattersRecommended minimum size: 323 points wide for a large visual, 158 for a small one. Font no smaller than nine points.
  3. Clean up noiseRemove axis titles, gridlines and legend; arrange navigation and slicers horizontally; reduce white space.
  4. Testing an interactionTooltips are disabled on the editing canvas but work in the app. Slicer selections on the canvas don't carry over to the grid layout.
✓ What this update adds to mobile: Audiences in the enterprise app now also work on iOS and Android, so each user sees exactly what's meant for them within the app — which significantly reduces the need for a separate mobile deployment per group.
Automatic responsiveness may clash with manual formatting. You can turn it off inGeneral > Properties > Advanced options.

Chapter VIII · Self-check

Quiz — 12 questions

One question at a time. A correct answer is colored green, an incorrect one red, and the correct answer is always revealed along with a full technical explanation.

What happens to a TMDL script you wrote in the browser after closing the tab?

explanation: This is one of four substantive differences between TMDL View in Desktop and the browser version. In Desktop, scripts are saved as part of the model, and in a PBIP project they come down as tmdl files in the TMDLScripts folder. In the browser, on the other hand, they are not saved at all and are deleted when the model or browser is closed — and even scripts previously saved in Desktop will not be shown there. Version history restores the the model after Apply, not the script you wrote.

To rename a column in TMDL, which object needs to be written as a script?

explanation: TMDL works in the object hierarchy of the tabular model, and renaming requires writing a script of the father of the object: a column belongs to a table, and a table belongs to the whole model. The reason is that the name is the object's identifier within its parent, so it's the createOrReplace operation on the parent that performs the replacement. It follows that a mass rename of tables needs to drag the whole model into the editor.

You downloaded the pbix, edited it in Desktop and republished. What happens to settings that were changed in the service in the meantime?

explanation: Publishing from Desktop is an operation of Full replacement of the model, not a merge. Desktop has no idea what happened in the service since the download, so it writes its own picture over everything. Changes made in the service don't sync back to the local file, and anything done there between the download and the publish is lost. This is why the only rule that works is a single source of truth per model: either Git and PBIP, or full management in the service — not a mix.

What's the risk of turning off Auto date/time from the browser in an enterprise model?

explanation: Auto date/time creates a hidden date table for every date column in an Import table, and the hierarchies users drag onto visuals are based on them. Turning the setting off deletes these tables, so any visual relying on such a hierarchy will show a broken-field error after the refresh. Note that this is one of only two settings in the dialog that take effect Immediately upon saving and not on the next refresh. The permanent fix is switching to an explicit date table and updating the reports.

What happens to the semantic model permission when a user is removed from an enterprise app?

explanation: This is the most important change in enterprise apps, and it's a security change, not a visual one. Propagated access applies both to the items and to the semantic models behind them, and the removal is consistent: there's no more dependent access left behind. In the old workspace apps, app permission and model permission were separate, so a removed user could remain with access to the data — and that was a silent exposure in every organization that turns over employees.

You applied a new theme and half the visuals didn't change. Why?

explanation: The priority order in formatting is: the base theme, above it a customized theme, and above both, formatting applied directly to a single visual in the format pane. So changing the theme only updates visuals that were left at default. The fix is to reset the relevant section in the format pane for every visual that was formatted manually — and not to do a Reset to default on the whole visual, since a full reset also removes button actions, conditional formatting, and field-based images.

How do you activate the Fluent 2 base theme in a report edited in the service?

explanation: In preview, the Fluent 2 base theme can only be turned on in Power BI Desktop, and the Customize current theme option and the options below it in the Themes menu aren't available in the service. To get the style in the service you have to build or update the report in Desktop and then publish. Also note that switching the base theme doesn't change the size of existing pages — only new pages get the new canvas.

Which settings in Model Options take effect immediately upon saving?

explanation: The settings split into two groups by what they change. Auto date/time and blocking DirectQuery change the model's structure and the permission to connect to it, so they take effect immediately. Type detection, Relationships, parallel loading and Locale affect Loading method of the data, so they only take effect on the next load or refresh. This distinction matters: changing the locale won't fix data that's already loaded until you run a refresh.

A model deployed through deployment pipelines — where can you edit it in the browser?

explanation: Browser editing is only supported in the pipeline's development environment; in test and production it's deliberately blocked, so that promotion between environments remains the only way to change production. This is one of five categories of models not supported for browser editing — alongside models that haven't been upgraded to the enhanced metadata format, models with automatic aggregations, models with a live connection, and models migrated from Azure Analysis Services. Hovering over the Open semantic model button will indicate which restriction applies.

How do you move a workspace app to an organizational app?

explanation: Microsoft has explicitly stated that there is no migration tool and no published timeline for ending support for Workspace apps, and they are fully supported in parallel. The planning implication: a new rollout project should start directly with enterprise apps, and an organization with existing apps should plan a gradual transition rather than waiting for a tool that does not exist. Build tip: first set up the broadest audience with all the items, then duplicate and toggle off visibility.

What happens to the data after Apply of a TMDL script that changed a Power Query expression?

explanation: TMDL changes Metadata only: it updates the object's definition in the model, but doesn't run a refresh and doesn't touch the report. So a change to a Power Query expression or a calculated column will sit in the model with no effect until you run a refresh of the table or model. The advantage of this behavior is that you can make dozens of structural changes without paying for a refresh on each one — the downside is that it's easy to forget to refresh and conclude the change didn't work.

After renaming a column in TMDL, what will the Power Query editor show?

explanation: The sync between the model table and the Power Query query is based on a property sourceColumn, which stays on the original name even after the column is renamed in the model. So the names become disconnected from each other: the editor will display sourceColumn, and renaming through the graphical interface won't add a rename step to the query as long as the two aren't identical. Anyone who wants full identity needs to also change sourceColumn in the script — otherwise it's worth documenting the separation so it doesn't confuse the team.
