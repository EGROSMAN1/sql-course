הפונקציה הראשונה

שלוש שורות, ואתם כבר מבינים את כל המבנה.

DAX

EVALUATE

מילת המפתח FUNCTION · שם · רשימת פרמטרים · חץ · גוף הפונקציה

פרק II · יסודות UDF

תיעוד וכללי שמות

פונקציה שאיש לא מבין איך לקרוא לה היא פונקציה שאיש לא ישתמש בה.

DAX
DEFINE
    /// מחשב אחוז רווחיות בצורה בטוחה מחלוקה באפס
    /// @param {NUMERIC} revenue - סכום ההכנסה
    /// @param {NUMERIC} [cost] - עלות, ברירת מחדל 0
    /// @returns אחוז רווחיות כמספר עשרוני
    FUNCTION Fin.MarginPct =
        ( revenue : NUMERIC, cost : NUMERIC = 0 ) =>
            DIVIDE ( revenue - cost, revenue )

EVALUATE
{ Fin.MarginPct ( 1000, 400 ) } // 0.6

ייחודיותשם ייחודי במודל, שאינו מתנגש בפונקציה מובנית או במילה שמורה כמו measure או function
נקודותמותרות למרחבי שמות כמו Fin.MarginPct — אך לא בהתחלה, לא בסוף ולא ברצף
תוויםמלבד נקודות: תווים אלפאנומריים וקו תחתון בלבד. בלי רווחים
שמות פרמטריםנקודות אסורות לגמרי, ואסור להשתמש במילה שמורה

איפה קוראים לפונקציה

אחרי השמירה למודל, הפונקציה מתנהגת כמו כל פונקציית DAX מובנית.

DAX

-- עמודה מחושבת (שימו לב להמרת הטיפוס)

-- חישוב ויזואל

DEFINE
    FUNCTION AddVat = ( amount : NUMERIC ) => amount * 1.18

✓ רקורסיה — פונקציה שקוראת לעצמה במישרין או בעקיפין — אינה נתמכת. הרכבה של פונקציות שונות כן.

פרק III · מערכת הטיפוסים

val מול expr

שתי פונקציות עם גוף זהה לחלוטין, ושתי תוצאות שונות. זה הנושא החשוב ביותר בשיעור.

DAX
DEFINE
    /// טבלה כערך: מקבלת טבלה שכבר חושבה
    FUNCTION CountRowsNow = ( t : TABLE VAL ) =>
        COUNTROWS ( CALCULATETABLE ( t, ALL ( 'Date' ) ) )

    /// טבלה כביטוי: מקבלת ביטוי לא מחושב
    FUNCTION CountRowsLater = ( t : TABLE EXPR ) =>
        COUNTROWS ( CALCULATETABLE ( t, ALL ( 'Date' ) ) )

EVALUATE
{
    CALCULATE ( CountRowsNow ( Sales ), 'Date'[Fiscal Year] = "FY2020" ),
    CALCULATE ( CountRowsLater ( Sales ), 'Date'[Fiscal Year] = "FY2020" )
}
הפונקציהמה היא מחזירהלמה
CountRowsNowרק את שורות FY2020הטבלה כבר סוננה לפני הכניסה לפונקציה, ולכן ה-ALL שבפנים כבר לא משנה דבר
CountRowsLaterאת כל השניםהפונקציה קיבלה ביטוי לא מחושב והעריכה אותו בעצמה תחת ALL, כלומר הסירה את הסינון החיצוני
הכלל שכדאי לשנן: פרמטר val מוערך אצל הקורא ולכן יורש הקשר שורה והקשר סינון. פרמטר expr מוערך בתוך הפונקציה ולכן יורש הקשר סינון בלבד.
✓ טיפ מקצועי: כשפרמטר expr עשוי לקבל מדד או נוסחה, כפו מעבר הקשר בתוך הפונקציה עם CALCULATE מפורש. כך הפונקציה עובדת נכון גם בשימוש שלא צפיתם.

    FUNCTION Stat.ModeX = ( e : ANYREF ) =>
        VAR newTable = ADDCOLUMNS ( TABLEOF ( e ), "expr", e )

פרק VIII · בדיקה עצמית

בוחן — 12 שאלות

שאלה אחת בכל פעם. תשובה נכונה נצבעת בירוק, שגויה באדום, והתשובה הנכונה תמיד נחשפת יחד עם הסבר טכני מלא.

מה מצב ההעברה של פרמטר שנכתב בלי שום רמז טיפוס?

הסבר: ברירת המחדל היא AnyVal val. משמעות הדבר שהארגומנט מוערך במלואו לפני הכניסה לגוף הפונקציה, והערך שכבר חושב הוא זה שנכנס פנימה. זו הסיבה שפונקציה פשוטה עובדת כמצופה בלי לציין כלום — אבל גם הסיבה שניסיון לשנות הקשר בתוך הפונקציה לא ישפיע, כי אין יותר ביטוי לשנות לו הקשר. התשובה 'תלוי בארגומנט' שגויה כי מצב ההעברה נקבע בחתימה הפונקציה, לא בקריאה אליה.

פרמטר במצב expr יורש איזה הקשר?

הסבר: פרמטר expr מועבר כביטוי לא מחושב ומוערך בתוך גוף הפונקציה, ולכן הוא רואה את הקשר הסינון ששורר שם אך לא את הקשר השורה של הקורא. פרמטר val, לעומת זאת, מוערך אצל הקורא ולכן יורש את שניהם. זו בדיוק הסיבה שאותו גוף פונקציה מחזיר תוצאות שונות בשתי הפונקציות CountRowsNow ו-CountRowsLater: באחת הטבלה כבר סוננה, ובשנייה ה-ALL בפנים עוד יכול להסיר את הסינון.

מה קורה כשפונקציה מפנה למדד שמוגן באבטחה ברמת אובייקט?

הסבר: OLS אינו עובר לפונקציות ולהפך — זו מגבלה מתועדת ולא באג. כשהפונקציה רצה תחת זהות שאין לה הרשאה למדד, המנוע מתנהג כאילו המדד אינו קיים כלל, מה שעלול להחזיר תוצאה שגויה בשקט במקום לחסום. ההמלצה הרשמית נגזרת מכך: אין לחשוף שמות של אובייקטים מוגנים בשמות הפונקציות ובתיאורים שלהן, וחובה לבדוק כל פונקציה תחת כל תפקיד לפני פרסום.

למה אסור להסתמך על סינון ברשת התוצאות של DAX Query View כדי לאמת נתונים?

הסבר: המיון והסינון הם פעולת ממשק על מה שכבר חזר מהמנוע, לא שאילתה חדשה. אם התוצאה נקטעה — במגבלת 15MB, במיליון ערכים לשאילתה, או ב-99,999 שורות בדפדפן — אתם מסננים חלק מהנתונים ומסיקים על הכול. לוולידציה אמיתית יש להעביר את הלוגיקה לשאילתה עצמה עם FILTER ו-ORDER BY ולהריץ מחדש.

רמז הטיפוס MeasureRef נדחה באתר הקריאה. מה הפתרון?

הסבר: זהו באג ידוע ומתועד: טיפוסי ההפניה הספציפיים — CalendarRef, ColumnRef, MeasureRef ו-TableRef — אינם מתקבלים בכל אתרי הקריאה, ודרך העקיפה הרשמית היא נפילה חזרה ל-AnyRef שהוא הטיפוס הכללי של המשפחה. האפשרות להעביר כערך שגויה כי הפניה חייבת להיות expr; שדרוג רמת תאימות לא רלוונטי כאן, כי אילו הייתה נמוכה מדי הפונקציה כלל לא הייתה נשמרת.

מהי רמת התאימות המינימלית הנדרשת לפונקציות מוגדרות משתמש?

הסבר: 1702 ומעלה. רמת התאימות קובעת אילו אובייקטים ומאפיינים המודל מסוגל להכיל בכלל, ולכן מודל ותיק שלא שודרג פשוט יסרב לשמור את הפונקציה — וזו הסיבה הראשונה לבדוק כשמשהו לא עובד. ב-TMDL View מוצג פרומפט שדרוג אוטומטי שמציין בדיוק איזה אובייקט מחייב את השדרוג.

בפונקציה עם שלושה פרמטרים שרק השני אופציונלי — כמה ארגומנטים חייב הקורא למסור?

הסבר: מספר הארגומנטים המינימלי — הארינות של הפונקציה — נקבע לפי מיקום הפרמטר הנדרש הימני ביותר, ולא לפי כמה פרמטרים אופציונליים יש. מכיוון שהפרמטר השלישי נדרש, חובה למסור שלושה ארגומנטים. מותר לדלג על השני בפסיק ריק בסגנון MyFunc(1,,3), וברירת המחדל שלו תיכנס לתמונה.

מה מייחד הערה שמתחילה בשלושה לוכסנים?

הסבר: התחביר /// נשמר אל תוך המודל כמאפיין תיאור של האובייקט, בדיוק כפי ש-TMDL תומך בו למדדים ולפונקציות. הערה רגילה עם // או /* */ נשארת בקוד השאילתה בלבד ולא מגיעה למי שקורא לפונקציה. בתוך הבלוק אפשר גם להשתמש בתגיות בסגנון JSDoc כמו @param ו-@returns כדי לתאר כל פרמטר בנפרד.

מה יקרה אם תשתמשו בתוך פונקציה בהפניה לא מוסמכת בסגנון [Amount] כשהכוונה לעמודה?

הסבר: שם לא מוסמך מפורש תמיד כהפניה למדד. זו מגבלה ידועה בתיקון הנוסחאות ובמעקב התלויות: אם התכוונתם לעמודה, השם לא ייכלל בגרף התלויות ולכן שינוי שם עתידי לא יתקן את הפונקציה והיא תישבר בשקט. הכלל המעשי: בתוך UDF תמיד לכתוב 'Sales'[Amount] עם שם הטבלה.

איפה מוצגת פריסת המובייל שבניתם לדוח?

הסבר: פריסת המובייל היא ארטיפקט נפרד שנשמר לצד פריסת הרשת, והיא נטענת רק על ידי אפליקציות Power BI ל-iOS ולאנדרואיד כשהמכשיר מוחזק לאורך. בדפדפן — גם בטלפון — תמיד תוצג הפריסה הרגילה, ולכן אי אפשר לבדוק פריסת מובייל דרך הדפדפן. הטיית המכשיר לרוחב מחזירה את התצוגה הרגילה גם באפליקציה.

מתי בוחרים UDF ולא קבוצת חישוב?

הסבר: פרמטרים מפורשים בחתימה הם היתרון המובהק של UDF: הקלט עובר ישירות, בלי לעבור דרך הקשר הסינון. כשאותה לוגיקה נקראת כמה פעמים באותה שאילתה, ההבדל הזה מצטבר גם לביצועים. קבוצת חישוב, לעומת זאת, נועדה בדיוק לתשובות א' ו-ג': להחיל וריאציית תצוגה אחידה על מדדים קיימים בלי לשכתב אותם.

פונקציה שמוגדרת עם ( t : TABLE ) ונקראת בתוך CALCULATE עם סינון שנה — מה היא תחזיר?

הסבר: בהיעדר מצב העברה מפורש, ברירת המחדל היא val. הטבלה מחושבת אצל הקורא — כלומר כבר מסוננת לשנה — ורק אז נכנסת לפונקציה, ולכן ALL שבפנים כבר לא יכול להסיר סינון מטבלה שחושבה. התיקון הוא הצהרה מפורשת: ( t : TABLE EXPR ). זו הטעות הנפוצה ביותר בכתיבת UDF ראשונה.
